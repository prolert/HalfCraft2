# Co-op M1 "Two Gordons, one Minecraft" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two players on `d1_trainstation_02`. The host runs `hc_host`, and the guest runs `connect <LAN IP>`. The guest's hidden Minecraft joins the host's Minecraft world on its own. Each player moves with their own Minecraft and sees the other's Minecraft body. Blocks and dug holes show up for both, and both can walk through the holes.

**Architecture:** The host runs a two-slot Source listen server (hl2dm) and its Minecraft opens its integrated server to LAN. Each machine keeps its own shared-memory link. The guest's client.dll writes the host's IPv4 (from the net channel) and the Minecraft port (from a replicated cvar) into its HostState, and its Minecraft joins that address. The host's server.dll streams collision around every player. The host's Minecraft server relays it to guests S2C. Guests send teleports and dug cells C2S. Valve's code gets M0's fixes and helpers that return the host.

**Tech Stack:** C++17 (MSVC; Source SDK 2013, hl2dm tree `source-sdk-2013/`), Java 25, Minecraft 26.3, Fabric Loader 0.19.5, Fabric API 0.161.0+26.3, Loom 1.18.3, JUnit 5, Python 3.13, ruff, clang-format/clang-tidy 22, GNU make.

**Spec:** `docs/superpowers/specs/2026-10-29-coop-m1-design.md`. Decisions are referred to by number: R1–R7 are the rulings, D1–D18 the decisions made there. Task 18 adds "## M1 acceptance results" to the spec.

## Global Constraints

- **Git.** Work on `main` and commit locally; never push. Another agent may commit on `main` at the same time:
  - `git add` only the task's files, then `git commit -F <message file> -- <those paths>`.
  - If git reports `index.lock`, wait a few seconds and retry.
- **Commit messages** start `feat:`, `fix:`, `chore:` or `docs:`, in lowercase English. The body says what changed and the evidence, and the last line is `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **Engines.** Co-op is hl2dm only. `make build` (both engines) must pass. The `hl2` tree and `source/sdk/halfcraft-hl2.patch` stay untouched.
- **Valve code** is edited only in `source-sdk-2013/src`, and goes back with `make patches ENGINE=hl2dm`. Before editing, `make setup ENGINE=hl2dm` prints `hl2dm sdk already patched at …`.
- **New HalfCraft `.cpp` files** go into `source/halfcraft_client.vpc` and/or `source/halfcraft_server.vpc` (the shared ones into both). Build with plain `make build` (no `NOPROJECTS`) after that.
- **The protocol** changes only in `protocol/schema/*.toml`, followed by `make proto`. Generated files are never hand-edited.
- **`source/src/core`** has no SDK, is C++17 with `inline` headers, and is tested by `tools/debug/core_tests.cpp` (`make core-test` → `core_tests: <n> checks passed`).
- **Warnings fail the build:** HalfCraft's C++, the core tests at `/W4 /WX`, and Java with `-Xlint:all -Werror`.
- **Style.** C++ comments lowercase with tabs (`make format`); Java uses Eclipse's formatter (`make format`); Python uses ruff. `make lint` must pass.
- **Host setup.** Never `coop 1` (R3): host setup goes only through `hc_host`.
- **Addresses.** Never connect to `127.0.0.1`. The LAN IPv4 comes from the host's `Network: IP <ip>, mode MP` line.
- **Link ids** (R7, D18): the host pair has none (today's names); the guest pair is `guest`.
- **Minecraft names:** `Gordon` for the host pair, `Gordon2` for the guest pair (D1).
- **Ports:** Source uses 27015 for the host (the guest copy moves its own sockets up by one). Minecraft LAN uses 25565 (`hc_coop_port`).
- **Online mode:** Minecraft takes offline accounts only when `FabricLoader.getInstance().isDevelopmentEnvironment()` (D1). Nothing else touches online mode.
- **In-game work** happens on `d1_trainstation_02`, in a test session on the HalfCraftTest desktop, through procedures P1–P6 below. Screenshots (`jpeg <name> 90`) are copied from `build/game-hl2dm/screenshots/` into `build/coop-m1/`.
- **Source launches.** Every dev or test start of Source adds `-multirun` (`run_hl2.py` does it for every start, with or without `--link`), so our tests never hold Source's one-instance mutex, which another project's `hl2.exe` on this PC needs. The release `HalfCraft.exe` is unchanged.
- **Shell.** Commands run from the repo root in PowerShell 5.1. Run `make build`, `make tidy`, `make mc` and Gradle tests in the background, with logs in `build/logs/`. Run `make build` only while no game runs.
- **Hands off** `tools/game/run_minecraft.py` (untracked, not ours). It imports `MINECRAFT_MUTEX`, `Session`, `ensure_minecraft_stopped` and `with_session` from `test_session.py`, so Task 2 keeps those four importable.

## Procedures (in-game)

`$ip` is the host's LAN IPv4. A mark is `$m = python tools/game/wait_log.py <log> --mark`, taken before the command. "Wait for `<p>` N s in `<log>`" is `python tools/game/wait_log.py <log> --after $m --pattern "<p>" --timeout N`. The logs are `hl2dm`, `hl2dm-guest`, `mc-test` and `mc-test-guest` (the last two from Task 2). Lines marked [mc] apply only when the task uses Minecraft.

- **P1 start, both pairs:**
  1. `make test-start`.
  2. [mc] In the background, `python tools/game/hidden_desktop.py make mc-test`, then, once `mc-test` shows `Setting user: Gordon`, `python tools/game/hidden_desktop.py make mc-test LINK=guest`. (Two Gradle runs started back to back both compile into `minecraft/build` when the sources changed; after a `make mc` there is nothing to compile and the wait can go.)
  3. In the background, `python tools/game/hidden_desktop.py make run WAIT=1`, then `python tools/game/hidden_desktop.py make run WAIT=1 LINK=guest`.
  4. Wait 600 s in `hl2dm` for `no bundled minecraft beside` (the game is up), and in `hl2dm-guest` for `\[halfcraft\] dig: ` (the first line `+con_logfile` catches: the guest's log misses everything before it). [mc] Also wait for `minecraft connected` in each.
- **P2 host:**
  1. `make cmd C="'hc_host d1_trainstation_02'"`.
  2. Wait 120 s in `hl2dm` for `2 player server started`, then 300 s for `map maps/d1_trainstation_02.bsp`.
  3. Take `$ip` from the `Network: IP ([0-9.]+)` line after the mark. If the line isn't there, use `(Get-NetIPConfiguration | Where-Object IPv4DefaultGateway).IPv4Address.IPAddress` (the first address may be a VPN adapter's, which needs `sv_lan 0`).
  4. `make cmd C="'sv_cheats 1'"`. [mc] Wait 120 s for `puppet on` in `hl2dm`.
- **P3 join:**
  1. `make cmd LINK=guest C="'connect $ip'"`.
  2. Wait 120 s in `hl2dm-guest` for `Connected to $ip`.
  3. [mc] Wait 180 s in `mc-test-guest` for `Connecting to $ip, 25565`, then for `puppet on` in `hl2dm-guest`.
- **P4 players:** `make cmd C="'hc_debug_players'"`, then read the `players:` and `player <n>` lines after the mark in `hl2dm`.
- **P5 stop:**
  1. [mc] Minecraft first: for each pid that `python tools/game/hidden_desktop.py --list` shows with a window titled `Minecraft*` (`java.exe` for the Loom clients; `javaw.exe` is Prism's, in a release), `python tools/game/hidden_desktop.py --close <pid>`. Wait 120 s for `Stopping!` in `mc-test` and in `mc-test-guest`.
  2. Then Half-Life: `make cmd LINK=guest C="'quit'"`, then `make cmd C="'quit'"`, then `Wait-Process -Name hl2mp_win64 -Timeout 120 -ErrorAction SilentlyContinue`.
  3. `make test-stop` must print `test session off`.
- **P6 respawn, on one copy** (`make cmd LINK=guest …` for the guest's, `make cmd …` for the host's), after a `kill` or `hc_mc kill @s` there. The game's rules here are the singleplayer ones (`CSingleplayRules::IsMultiplayer()` is false), so `mp_forcerespawn` does nothing: a dead player respawns only after every button is up and then one is pressed. (With Minecraft on, a dead player's input is Source's again, so a button sent to Source reaches it.)
  1. Wait 7 s (the death animation runs up to 60 thinks of 0.1 s).
  2. `make cmd [LINK=guest] C="'+jump'"`, wait 0.3 s, then `make cmd [LINK=guest] C="'-jump'"`.
  3. P4, repeated every 2 s for up to 10 s, until that copy's `player` line shows `alive 1`.

## Review Focus

These are the cases outside the tasks' own tests most likely to bite, most likely first. Each has a test added to the task that owns it:

1. **The host dies in Minecraft and respawns.** Vanilla moves the host's `ServerPlayer` to the end of the player list. Mobs, actors and block damage must still follow the host, and a guest must never be taken for the host. Task 12: `hostIsFoundWhereverItIsInTheList`. Task 18: step 7.
2. **The guest leaves, or the host quits, mid-session.** The guest's Minecraft goes back to its own world once, without a join loop or a stuck title screen. Its relayed collision is cleared, and the host's relay forgets it. Task 13: `soloLeavesTheHostsWorld`, `guestRetriesOnlyAfterTheRetryTime`. Task 16: step 9.
3. **A collision message larger than the S2C payload cap (8 MiB, sent with `registerLarge`; 1 MiB without it), or a relayed `byte[]` read with `JAVA_INT`.** The first would kick the guest; the second throws on a misaligned segment. Task 15: `aTooBigUpdateIsNeverRelayed`, `relayedRegionIsReadLikeTheRings`.
4. **Port 25565 already taken on the host.** The host's Minecraft reports `failed` and says why. `hc_coop_mc_port` stays 0, guests wait, and the host tries again every 5 s. Task 13: `hostTriesAgainOnlyAfterTheRetryTime`. Task 16: step 8.
5. **A guest that Source places before any collision has reached it** (the join, a respawn). The guest is held, not dropped into the void, so the relay sends the regions nearest the guest first. Task 15: `dueIsNearestFirstAndSkipsWhatWasSent`. Task 16: step 6. Task 18: step 7.
6. **A jump landed elsewhere, predicted again.** Prediction now runs for the host too, so `client_jump_landed_elsewhere` is called again for a landing it already has. `hc_jumps.cpp` keeps the latest landing and ignores one at the spot it just resynced to, so one jump must cause one resync, not one per re-prediction. Task 18: step 8.

The tools derive file names with `link.file_tag(link_id: str) -> str`, which can't collide: lowercase letters, digits, `_` and `-` as they are, each uppercase letter as `~` and its lowercase (an id has no `~`). `guest` stays `guest`, `B` is `~b`. It names `console-<tag>.log` and `hl2-<tag>.pid`. (The other way, rejecting a second id that differs only in case, would need the tools to know every other id.) The Minecraft side of M1 has `guest` only, with fixed names (below).

      - `COL_REGION` closes the update: the region's messages become the pending ones plus this one. The version goes up only when the bytes differ from the stored update (D7). Versions come from one counter that a clear doesn't reset: a changed or new update takes the next number, so a region rebuilt after a clear never repeats a version a guest was sent.
      - An update with a message over `MAX_PAYLOAD_BYTES` removes the region instead, `skipped()` goes up by one, and it is logged once per region.
      - `COL_CLEAR` empties everything (the counter stays), sets `epoch()` to the payload's int, counts in `clearCount()` and sets `sawClear()`.

    - `static void tick(MinecraftServer server)` (`END_SERVER_TICK`):
      - Every guest is a player that isn't `HostPlayers.isHost` and is in the mirror level.
      - When the store's `clearCount()` changed since a guest's last send (not only the epoch: on `EV_COLLISION_LOST` server.dll resets with the same epoch), that guest first gets `COL_CLEAR(epoch)` and its sent map starts over.
      - Each guest gets up to 32 due regions a tick, around its block position, each region's messages in order.
      - When a guest's whole area has gone out the first time, log `HalfCraft: relayed {} collision regions to {}`.
    - `static void forget(UUID player)` runs on `DISCONNECT`.
  - `HostCollision`:
    - `static void dispatch(int type, MemorySegment s, long payload)` is package-private: today's switch.
    - `static void dispatchCopy(int type, byte[] payload)` is package-private: it copies into `MemorySegment.ofArray(new long[(payload.length + 7) / 8])` and dispatches.
    - `public static void acceptRelayed(int type, byte[] payload)` queues for the consumer thread.
    - `public static void setRelayed(boolean relayed)`: on a change, the consumer clears the store (epoch −1) before its next message.

    - Otherwise each ring message also goes to `CollisionRelay.offer`.
  - `CoopClient`: the `collision` receiver calls `HostCollision.acceptRelayed`. `setRelayed(joined())` runs every frame.
